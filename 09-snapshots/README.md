# 第 9 章：工作区隔离与快照冻结

状态：已实现工作区复制、只读冻结、源变化检测与一致性校验。本章不执行真实 Agent，也不判断代码是否正确；它只回答“候选到底是哪一份内容”。

## 为什么需要快照

编码结束后，工作区仍然是一个会变化的地方：验收命令可能生成文件，审查进程可能顺手改代码，开发者也可能继续编辑。如果验收、审查和最后交付各自读一次工作区，它们看到的可能不是同一份内容；“三项都通过”就变成了对三个不同版本的模糊结论。

快照把“候选”固定下来：

- 复制发生在编码停止之后，复制的是磁盘上的完整工作区；
- 复制完成后冻结为只读，验证与审查读同一棵树；
- 复制期间源目录若发生变化，本次快照直接拒绝，不把两个时刻混在一起；
- 交付时给出清单摘要，后续证据可以绑定到这份摘要，而不是“大概是那个版本”。

一个诚实的边界：快照能捕获磁盘上的一切，包括未提交修改和未跟踪文件；但编辑器里尚未保存的缓冲区不在磁盘上，任何工具都看不见。生成候选前必须停止写入并保存文件。

## 设计思路

| 决策 | 理由 |
| --- | --- |
| 复制工作区，而不是 `git checkout` 某个提交 | 候选必须包含未提交修改和未跟踪文件；从 HEAD 重新检出会悄悄丢掉它们。快照的输入是磁盘状态，不是版本库状态 |
| 默认排除 `.git` 与 `target` | 版本库元数据和构建产物不是候选内容；把它们复制进来既慢又会制造无意义的差异。排除项可按名称配置 |
| 复制结束后重新扫描源目录并比对摘要 | 这是“停止写入”的可执行检查：只要复制期间有文件被改、增、删，`SourceChanged` 就拒绝本次快照，不发布半成品 |
| 每个文件 SHA-256，清单再算聚合摘要 | 单文件摘要用于定位差异，聚合摘要用于绑定候选版本；同样内容在不同快照 id 下得到相同聚合摘要 |
| 先写临时目录，再 `rename` 发布 | 复制或清单写入失败时不会留下占用正式 id 的半成品；失败路径由清理守卫回收临时目录 |
| 冻结：去掉文件与目录的所有写位（保留读/执行位） | 普通写入、新建和删除都会得到 `Permission denied`；可执行脚本仍能执行。这是流程约束，不是安全沙箱 |
| 冻结后仍可 `verify` | 只读权限可能被同用户进程用 `chmod` 绕过；验证结束时重新计算内容摘要并检查可写位，改动会被发现并拒绝 |
| 拒绝符号链接与特殊文件 | 符号链接可能把工作区外的内容带进候选；FIFO、设备文件也不属于源码。显式拒绝比静默跟随安全 |
| `Snapshot` 不实现自动删除 | 快照是候选交付物，生命周期应由调用方管理；只有测试/演示用的 `TempDir` 在 `Drop` 时清理 |
| 清单放在快照目录之外、单独只读 | 文件树保持“只有源码”的干净形态；清单被篡改时 `open` 会因摘要不符而拒绝 |

## 快照与冻结流程

```text
Snapshot::create(source, root, id)
  │
  ├─ 校验 id；canonicalize 源目录与快照根
  ├─ 扫描源目录（排除 .git / target / 快照根）
  ├─ 复制到 <root>/.<id>.tmp-<nonce>/，逐个计算 SHA-256
  ├─ 重新扫描源目录，比较复制结果
  │     └─ 有变化 → SourceChanged，删除临时目录，正式 id 不被占用
  ├─ 冻结：去掉写位，保留读/执行位（目录从深到浅）
  ├─ 写 <root>/.<id>.manifest.tmp-<nonce>，设为 0444
  ├─ rename 临时目录 → <root>/<id>
  └─ rename 临时清单 → <root>/<id>.manifest.json

Snapshot::verify()
  ├─ 遍历快照文件，逐个重算 SHA-256
  ├─ 与清单比较：changed / added / removed
  ├─ 检查所有文件与目录是否仍为只读
  └─ 重算聚合摘要并与清单记录比较
```

`verify` 的检查顺序是先内容、后权限、最后聚合摘要。内容变化和权限松动都会进入 `Inconsistent`，一次报告全部差异；任何一项不通过都不返回成功。

## 核心接口

| 接口 | 作用 |
| --- | --- |
| `Snapshot::create(source, root, id)` | 用默认选项创建并冻结快照；目标已存在时拒绝覆盖 |
| `Snapshot::create_with_options(..., &SnapshotOptions)` | 配置排除项、是否重扫源目录 |
| `Snapshot::open(root, id)` | 从磁盘重新加载清单；校验 id、排序与摘要，但仍需调用 `verify` |
| `Snapshot::path()` | 只读文件树根目录 |
| `Snapshot::manifest()` / `manifest_path()` | 内存清单与磁盘清单路径 |
| `Snapshot::digest()` | 候选聚合摘要，供后续证据绑定 |
| `Snapshot::verify()` | 验证结束后检查内容与权限；返回 `VerifyReport` |
| `Snapshot::remove()` | 恢复写权限并删除快照目录与清单 |
| `TempDir::create(prefix)` | 测试/演示用临时目录守卫，`Drop` 时递归清理 |

清单结构：

```json
{
  "snapshot_id": "candidate-1",
  "digest": "a671a2d6…",
  "entries": [
    { "path": "notes.md", "size": 46, "sha256": "83546b48…" },
    { "path": "src/main.rs", "size": 41, "sha256": "b9264169…" }
  ]
}
```

`entries` 按路径严格排序，路径统一用 `/` 分隔且必须是 UTF-8；排序让摘要可重复，UTF-8 限制避免清单在不同平台上出现无法表示的名字。非 UTF-8 路径会被 `NonUtf8Path` 拒绝。

## 运行实验

从仓库根目录运行，无需账号或网络：

```bash
cargo run -p chapter-09-snapshots
```

演示会创建临时工作区，模拟“编码已停止”的状态，然后生成快照、尝试写入并执行一致性检查。预期输出：

```text
工作区：/var/folders/.../workspace
模拟编码已停止：main.rs 是未提交改动，notes.md 是未跟踪文件。

== 快照清单 ==
    46 B  83546b48c873  notes.md
    19 B  b9f82c414bb0  src/greeting.txt
    41 B  b9264169811d  src/main.rs

快照目录：/var/folders/.../snapshots/candidate-1
清单文件：/var/folders/.../snapshots/candidate-1.manifest.json
快照摘要：a671a2d6813d7314dde68a35d4e227991326125d287211fa9cb04ab1e91d54ad

.git 与 target 未进入快照：它们不是候选内容。

== 冻结：审查方尝试写入 ==
写已有文件被拒：Permission denied (os error 13)
新建文件被拒：Permission denied (os error 13)

== 验证结束：检查快照一致性 ==
一致：3 个文件，摘要 a671a2d6813d7314dde68a35d4e227991326125d287211fa9cb04ab1e91d54ad
审查读取 main.rs：fn main() { /     println!("候选 v2"); / }

边界：只读权限拒绝普通写入；同用户进程若先 chmod 再写，verify 会发现并拒绝。
```

四个观察点：

- `notes.md` 没有经过 git 跟踪，仍然进入快照；候选不是“HEAD 的内容”；
- `.git` 与 `target` 不在清单里，排除规则生效；
- 两次写入都被操作系统拒绝，说明冻结不是口头约定；
- 摘要一致，说明验证前后是同一份候选。

对真实目录生成快照：

```bash
cargo run -p chapter-09-snapshots -- . /tmp/rast-snapshots repo-1
```

快照会保留在 `/tmp/rast-snapshots`，这是预期行为：候选交付物不因进程退出而消失。需要清理时用库的 `Snapshot::remove()`。不要让快照根目录等于源目录；根目录位于源目录内部时会被扫描排除，但建议放到仓库之外。

## 边界的真实成本

**未提交不等于未保存。** 快照复制磁盘文件，因此 git 未提交修改、未跟踪文件、甚至被 `.gitignore` 忽略的文件（只要没在排除名单里）都会进入候选。编辑器里尚未落盘的内容无法被任何外部工具捕获，这是流程约束，不是本实现的缺陷。

**只读不是安全沙箱。** 文件属于当前用户，同一用户的进程可以先 `chmod` 再写。`verify` 能发现验证结束后的内容或权限变化并拒绝结果，但不能阻止一个在验证过程中持续篡改的恶意进程。真正的权限隔离、只读挂载或容器边界属于第 17 章的安全验收范围。

**排除规则是名称匹配。** 任何层级下名为 `.git` 或 `target` 的目录/文件都会被跳过。如果项目里恰好有同名源码目录，需要用 `SnapshotOptions` 调整。排除项不进入清单，因此它们的后续变化不会触发 `SourceChanged`；这是有意的：候选只对纳入清单的内容负责。

**重扫的代价是双倍读取。** `verify_source` 默认开启，复制后会把源目录再完整读一遍并计算摘要。大仓库会明显变慢；关闭它可以省掉这次读取，但也失去了“复制期间没有写入”的证据。首版选择证据优先。

**清单自身也需要锚点。** `open` 会检查清单 id、排序和摘要，但一个能同时改写条目和摘要的进程仍可伪造一份自洽的清单。要把候选摘要变成可追责的证据，需要把它写到快照之外并由验收记录引用，这正是第 11 章的工作。

**崩溃窗口。** 临时目录和清单都用临时名字，正常失败会被清理；进程在 `rename` 之间崩溃时可能留下 `.<id>.tmp-*` 或临时清单。它们不会占用正式 id，但需要运维清理。第 14、15 章的持久化与恢复会对账这类残留。

**验证可能也需要写权限。** 快照本身是只读的；如果验收命令要生成构建产物，应把输出目录指向快照之外（例如设置独立的 target 目录），或先把快照复制成一次性的可写工作区。不要为了跑验收而解冻候选快照，否则验证前后的内容不再是同一份。

**平台差异。** Unix 上通过去掉写位得到 `Permission denied` 完成验收；非 Unix 平台只能可靠地设置文件只读，目录写保护不完整，因此写入拒绝测试以 `cfg(all(test, unix))` 为条件。当前验收范围是本机 macOS/Linux。

## 验证与完成标准

```bash
cargo test -p chapter-09-snapshots
cargo check --workspace
cargo fmt --all --check
```

测试覆盖：

- 未提交改动、未跟踪文件进入快照，`.git` 与 `target` 被排除；
- 符号链接被拒绝，且不留下临时目录或正式清单；
- 冻结后写已有文件、新建文件、删除文件都被拒绝；
- 内容修改、新增、删除都被 `verify` 报告；
- 仅改权限、不改内容也会被 `verify` 报告；
- 复制期间源文件变化返回 `SourceChanged`，正式 id 不被占用；
- 相同内容、不同 id 得到相同聚合摘要；
- 重复 id 被拒绝；非法 id（空、`.`、`..`、含分隔符）在触碰文件系统前被拒绝；
- `open` 能重新加载并通过验证，篡改清单摘要会被拒绝；
- `TempDir` 的 `Drop` 能清理已冻结的快照。

完成本章后，你应能说明：为什么复制工作区而不是检出某个提交、为什么复制后要重扫源目录、只读权限与安全沙箱的差别，以及 `verify` 到底证明了什么、没有证明什么。

## 动手练习

1. 给命令行加一个 `--exclude` 参数，把它传给 `SnapshotOptions::exclude_names`；观察排除项如何改变清单摘要。
2. 在演示里模拟一次“审查方先 `chmod` 再写”，确认 `verify` 返回 `Inconsistent`，并打印 changed 与 writable 两个列表。
3. 把 `verify_source` 设为 `false`，在复制后钩子里修改源文件，观察快照仍被接受——思考这时快照代表的是哪一个时刻。
4. 给 `Snapshot::verify` 增加“逐文件报告”的输出格式，让它能直接作为第 11 章证据记录的一部分。

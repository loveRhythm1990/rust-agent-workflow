# 第 7 章：受控执行适配、超时与取消

状态：已实现受控执行机制：固定程序与参数、限时、超时或取消后清理整个进程组。本章执行的都是本地固定程序；真实 CLI 的受控调用由第 10 章接入，机制在此先行验收。

## 为什么需要受控执行

从这一章起，控制器要真正启动外部进程了。前面的委派、状态机都假设“执行者会回来”——现在要回答的是：进程跑飞了怎么办？预算用完了怎么停？停完会不会留下一堆孤儿进程？

用户任务最多能消耗多少时间，不该由执行者的自觉决定。外部工具（pi、Codex CLI、Claude Code CLI）自己还会再生子进程：只杀直接子进程，孙进程就会变成孤儿继续消耗机器。“限时 + 整组清理”是预算真正可执行的前提，也是第 13 章预算、第 15 章恢复能够落地的地基。

## 设计思路

| 决策 | 理由 |
| --- | --- |
| 固定可执行文件与参数，不经过 shell | shell 拼接等于把命令行交给字符串内容决定；受控执行从一开始就不提供这个入口。生产路径 `ExecutionRequest` 只有程序路径和参数数组，没有“执行字符串”这种字段 |
| 非零退出、超时、取消都是枚举值，不是异常 | 与第 3、4 章“运行事实与质量结论分开”一脉相承：`Failed(1)` 和 `TimedOut` 是记录，交给决策环节；程序本身不崩溃 |
| 用 tokio 异步等待而非线程轮询 | 超时需要“等进程”与“看时钟”并发进行；`tokio::time::timeout` 把两件事合成一次 await，也是本章 Rust 配套的主线 |
| Unix 上让子进程独立成为进程组长，杀负 pid | 外部工具会再生子进程；只有整组终止才能保证没有孤儿。杀单个 pid 对孙进程无效 |
| 边跑边读 stdout/stderr | 管道容量有限，进程写满输出而不被读就会永远卡住；并发读管道是受控执行的一部分，不是优化 |
| stdin 一律关闭 | 委派的执行者不应期待交互输入；stdin 关掉，等待输入的进程会立刻拿到 EOF |

## 运行实验

以下命令从仓库根目录运行；只依赖系统自带程序（`echo`、`sleep`、`false`、`pgrep`），无需账号。

```bash
cargo run -p chapter-07-process
```

预期输出（五个实验依次进行）：

```text
== 实验一：固定命令成功 ==
程序：/bin/echo 第 7 章：受控执行
结果 Completed（退出码 0），用时 5ms
stdout：第 7 章：受控执行

== 实验二：非零退出码被记录 ==
程序：/usr/bin/false
结果 Failed（退出码 1），用时 4ms
非零退出码是运行事实：记录下来交给决策，而不是当场崩溃。

== 实验三：超时终止整组 ==
程序：/bin/sleep 10（预算 1 秒）
结果 TimedOut（超时，进程组已终止），用时 1003ms
预算耗尽即终止：进程组按时清理，不等待进程自觉退出。

== 实验四：取消并验证无残留 ==
程序：/bin/sh -c sleep 30（500ms 后取消）
结果 Cancelled（取消，进程组已终止），用时 504ms
残留检查：pgrep 未发现任何 sleep 30，整组清理通过。

== 实验五：启动失败如实报告 ==
启动失败：无法启动 /definitely-not/a-real-program: ...（不会伪装成执行成功）
```

四个关键点：

- 实验二：`false` 的退出码 1 被记录为 `Failed(1)`——调用它的控制器还活着，这个事实以后会交给第 4 章 `decide`。
- 实验三：1 秒预算一到，`sleep 10` 被整组终止，用时约 1003ms 而不是 10 秒。
- 实验四：用 `/bin/sh` 派生孙进程（`sleep 30` 是 sh 的子进程）——生产路径只跑固定程序，这里专门验证整组清理对“会再生子进程的工具”同样成立；取消后 `pgrep` 找不到任何残留。
- 实验五：启动不了就明说，不把不存在伪装成"退出码 0"。

## 实现结构

- [src/lib.rs](src/lib.rs)：`ExecutionRequest`、`ExecOutcome`、`Execution::spawn / settle / cancel`，含异步测试。
- [src/main.rs](src/main.rs)：五个实验的演示。

一次执行的生命周期只有两条路：

```text
Execution::spawn(request)
   ├── settle(timeout) ──► 正常结束 → Completed / Failed(code) / Killed
   │                     └─ 超预算 → 杀进程组 → TimedOut
   └── cancel() ──────────► 杀进程组 → Cancelled
```

## 与第 6 章选型的衔接

第 6 章选了 pi 作为已候选委派接口。本章的机制是为"任何外部 CLI"准备的：固定路径与参数表、限时、整组清理，不绑定具体工具。pi 的真实调用（路径、`--print`、`--mode json`、`--session-id` 等参数）在第 10 章作为参数表接入，届时还要验证：pi 被整组杀死后，其会话文件与子进程是否一致地清理。

## 边界的真实成本

本章只管"进程跑多久、怎么停、停干净了没有"。它不判断输出内容是否可信（那是第 8 章报告校验和第 11 章证据的事），也不限制 CPU、内存或文件写入——预算与权限的完全形态分散在第 9、13、17 章。Windows 没有进程组语义，`kill_group` 在非 Unix 平台退化为只杀直接子进程；本项目当前验收范围是本机 macOS/Linux。

完成本章后，你应能说明：为什么非零退出码不是异常、为什么必须杀进程组而不是杀单个进程、以及取消之后怎么证明"没有残留"。

## 动手练习

1. 把实验三的预算改成 3 秒，观察用时记录随之变化；再把 `sleep 10` 改成 `sleep 1`，观察预算没用完就正常结束。
2. 给 `ExecutionRequest` 加一个 `stdout_limit_bytes` 字段并实现:超过限制就读到上限为止——思考:这该记录成 Completed 还是另一种结局?
3. 用 `yes` 这类疯狂输出程序跑一次,体会边读边收的必要性:把读管道的两个 `tokio::spawn` 临时删掉再跑,看看会发生什么(记得改回来)。
